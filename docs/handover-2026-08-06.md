# Handover — 6 August 2026

## The theme of the day

Every problem hit today was one disease: **the harness loses anything that exists only as
prose in an agent's reply, or only as a line in a plan file nobody accounts for.**

Four instances were fixed structurally (v0.51–v0.56): pushes (`verify` on dev-promote
stages), refusals (`BLOCKED:`), operator actions (`ACTION:`), and route drift
(`addMissingStages`). A fifth was found at the end of the day and is **not fixed** — it is
the top item below.

## 1. Plan-step accounting — BUILT in v0.57.0

### What happened

NMGB-2792's live plan had a numbered step §4: "post-deploy data rebuild — reload each BS1
file from period 244 onward and rebuild the two EV Share `Bespoke_KPIData` elements". The
deploy stage shipped the migration, the flag and the procs. **It did not do §4, and it
passed.** The gap surfaced in production as a scorecard tile showing 0.0%, found by hand.

Diagnosis, from the agent that eventually investigated: `Bespoke_KPIData` on
`NissanGB.live` has zero rows with `DataViewId = 4` for elements 29/30 in any period. The
deployed procs are correct and the staging table is clean — `p_Bespoke_KPIData` was simply
never re-run for periods 244+, so `p_Bespoke_Scorecard` falls back to `ISNULL(...,0)`.

**The live data rebuild was still outstanding as of this handover.** It changes live
production data and was deliberately left for a human to authorise.

### Why the existing mechanisms did not catch it

- `verify` would need a ticket-specific post-condition query. It cannot generalise.
- `DEFERRED` catches work a stage *declines*. This stage did not decline §4; it simply
  did not do it, and said nothing.
- The plan is a markdown file of numbered steps. The stage that executes it self-reports
  "done" for the stage as a whole. **There is no per-step accounting**, so a skipped step
  is indistinguishable from a completed one.

### The fix

A stage executing a numbered plan must account for **every** step: done, or explicitly
deferred with a reason. The engine refuses to pass the stage while any step is
unaccounted for. Same shape as `DEFERRED`/`BLOCKED`/`ACTION` — a marker in the reply,
parsed and held on the pipeline — but keyed to the plan file's numbered steps rather than
to free prose.

Design notes before starting:

- The plan file is written by an earlier stage and read by a later one, both cold sessions.
  Step identity therefore has to come from the file itself (numbered headings), not from
  anything held in a session.
- Settling a step must **require a sentence**, exactly as `resolveDeferral` does. A tick
  reproduces the gap, because what was missing was knowledge of whether the step ran.
- Hold in front of stages that ship, not every stage — the same reasoning as
  `nextAction`'s `deferredWork` hold. Most unexecuted steps are harmless; holding
  everything is how a safety net gets switched off.

## 2. Worktree claims — BUILT AND WIRED in v0.57.0

`src/domain/worktreeLease.ts` + 19 tests, all passing. Pure, vscode-free.

Solves two problems: stages create worktrees (`promote/*`, publish trees) that the
extension never recorded, so nothing was cleaned up and nothing could detect two tasks
overlapping on one worktree.

- `decideClaim` → `create` / `reuse` / `conflict`. **Idempotent**: asking twice for the
  same path and branch yields `reuse`, so a re-run stage need not know whether the last
  attempt got that far. Conflicts are reported and name the holder, never forced — forcing
  the wanted branch over whatever is there is how two promotions interleave.
- `planCleanup` → `remove` plus `retain`-with-reason, so a skip is never silent. Refuses
  on dirty (**including untracked**) or unmerged commits.
- `TaskWorkspace.worktreeClaims?: WorktreeClaim[]` added — optional, so no migration.

**The load-bearing distinction is `created` versus borrowed.** A task that created
`promote/NMGB-2792-uat` should remove it; a task that borrowed the standing
`qube-publish-sm` must leave it, or the next publish has nowhere to run. Recording
"worktrees this task used" would conflate them and delete shared infrastructure.

**Never deletes branches.** A worktree is a checkout and can be recreated; a branch may
hold the only copy of its commits.

### Remaining work

Wire it: a git-service method to gather `WorktreeFacts`/`CleanupFacts`, record a claim
wherever a stage creates a worktree, and run `planCleanup` when a task completes. Also
worth surfacing `conflict` as a stage hold rather than letting the agent discover it by
reading `git worktree list`.

## 4. Verify-command substitution — BUILT in v0.57.0

`verify` commands are passed to the shell verbatim, so a stage cannot name the task,
branch or ticket it is running for. Hit twice today:

- `Test-PublishWorktreesReady.ps1` cannot reject a worktree parked on *another* ticket's
  promotion when run from a route, because it does not know its own ticket. It degrades to
  an existence check.
- The same check demands all three publish worktrees regardless of ticket, when a
  NissanGB-only ticket needs only `qube-publish-sm`.

Adding `${taskName}` / `${branch}` / `${baseBranch}` substitution would fix both.

## Addendum — v0.57.0, 6 August 2026 (evening)

All five items above were worked. What actually shipped, and what did not:

**1. Plan-step accounting — built.** `domain/planSteps.ts`, `planFile` on a route stage,
per-step records on the stage, `approveStage` refusing a stage with an unaccounted step,
and a not-done step becoming a deferral so it inherits the shipping hold and the
settlement-needs-a-sentence rule. A stage whose plan file is missing is not run at all.

**2. Worktree claims — wired.** `services/worktreeClaimService.ts` over the existing
domain. Claims are *detected* by comparing the worktree list either side of a
`mayChangeBranch` stage, because the agent creates them and there was no call to hook. A
conflict now holds the stage. Cleanup is offered when a route completes and only ever
removes what the task created, clean and merged.

**3. Verify All — released**, with the version bump the earlier note asked for.

**4. Verify-command substitution — built.** `domain/commandPlaceholders.ts`.

**5. SQL file encoding — pre-flight complete, no file converted.** Committed to the app
repo's DEV as `2600082f1`, with `tools/sql/Convert-SqlFileEncoding.ps1` and the spec
updated. Two results worth carrying forward:

- Exactly **one** of the 10,590 files can lose data on conversion, and it is named in the
  spec. Everything else without a BOM is already valid UTF-8.
- The plan's assumption that this is a one-time rewrite with nothing to keep right is
  **wrong**. `Export-SqlBaseline.ps1` is where the UTF-16 files came from and would
  recreate them on the next baseline export, and `Invoke-DatabaseImportRoutine.ps1` reads
  with a hardcoded UTF-16 decode, so after a conversion it would read every file as
  garbage. Those four call sites must land in the same commit as the bulk convert, and
  were deliberately left alone so that landing the exporter fix early cannot turn the next
  baseline export into an uncoordinated partial conversion.

Still needing a human: the bulk convert itself (one sitting, worktrees closed), `sqlcmd`
against a scratch database, a converted folder deployed to dev, and the live data rebuild
for NMGB-2792 §4 that item 1 was written about — it changes live production data.
